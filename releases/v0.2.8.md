# Solo VPS v0.2.8 — Coolify 4.7.8

This alpha maintenance candidate prepares the reviewed **Coolify 4.7.3 → 4.7.8** transition, including upstream 4.7.6/4.7.7 dependency security fixes and the 4.7.8 persistent-volume regression fix. Sentinel **1.1.5** and Traefik **3.7.16** remain unchanged.

## Compatibility and upgrade

- Already on 4.7.8: use the exact published Solo VPS source tag when available and run `make verify-coolify`, `make verify` and `make audit`; no second Coolify upgrade is necessary.
- On 4.7.3: retain external controller state, prepare a reviewed source checkout, verify recovery inputs, pause deployments/settings changes, confirm Sentinel In Sync, and run `make coolify-upgrade-preflight` with the exact configured HTTPS Sentinel URL. Then use the confirmation-gated `make coolify-upgrade` and the three read-only post-upgrade checks. Do not install 4.7.7 first.
- On earlier versions: follow the documented preceding releases to 4.7.3 before this transition. The manifest does not authorize an arbitrary direct jump.
- See the [English update guide](https://paracosm17.github.io/solo-vps/operations/updates/) and the [Russian guide](https://paracosm17.github.io/solo-vps/ru/operations/updates/). Database migrations cannot be undone by downgrading the container image.

## Changes

- Pin the exact upstream 4.7.8 production Compose artifact with SHA-256; the base Compose and environment template remain byte-identical to 4.7.3. Preserve loopback-only management ports, automatic-upgrade disablement and the guarded checkpoint/transaction/forward-resume mechanism.
- Verify both control-plane PostgreSQL and Redis health statuses without printing their healthcheck commands or secrets. Retain exact reviewed Sentinel index/config identities on both sides.
- Review deduplicated resource ENV records, WebSocket-domain normalization, cleared legacy response-text healthchecks, public-preview secret restrictions, Compose include/env_file handling, storage-path behavior and scoped API/SSO changes. Existing service images are not automatically upgraded; verify actual mounted data before modifying persistent storage or redeploying.
- Update EN/RU documentation and add a [source review](https://github.com/paracosm17/solo-vps/blob/main/reviews/2026-11-26-coolify-478-source.md).

## Runtime and validation

On the existing maintained production VPS, the operator completed the guarded 4.7.3 → 4.7.8 transition: upgrade `ok=141 changed=10 failed=0`; dedicated `verify-coolify` `ok=57`, aggregate `verify` `ok=164`, and `audit` `ok=96`, all with changed=0 and failed=0. The control-plane health, realtime and terminal endpoints returned 200; all 17 containers were running, the control-plane dependencies, Sentinel and proxy were healthy, and the pending transaction was cleared. See [bounded production evidence](https://github.com/paracosm17/solo-vps/blob/main/reviews/2026-11-26-coolify-478-production.md).

The tested runtime source passed hosted fast-source and strict docs build and operator-run source validation. No claim of new disposable V3, fresh-install V4, app-specific HTTPS/API/volume redeploy smoke, or independent database restore is made. The mandatory automatic local checkpoint succeeded; no new off-site or application backup validation was performed for this update at operator request. The host reports a pending OS reboot, separate from the platform upgrade. Existing guidance to verify recovery inputs remains in force.

# Solo VPS v0.2.5 — Coolify 4.5.0 maintenance alpha

The reviewed transition is **Coolify 4.4.6 to 4.5.0**, including the upstream 4.4.7 security release. Sentinel is **1.1.2**; Traefik stays **3.7.14**. Solo VPS remains an alpha for one Ubuntu 24.04 application VPS.

## Update

Prepare a new v0.2.5 checkout with the existing external configuration and inventory; retain the previous source. Follow [How to update](https://paracosm17.github.io/solo-vps/operations/updates/) ([русский](https://paracosm17.github.io/solo-vps/ru/operations/updates/)). Earlier installations must reach the documented 4.4.6 origin first.

Pause deployments/settings changes and retain a fresh authenticated off-host Coolify backup with the original APP_KEY, plus separate application-data backups. Run `coolify-upgrade-preflight` with the exact Sentinel HTTPS URL, then the confirmed `coolify-upgrade`. Finish with `verify`, `audit` and real application checks. No proxy, OS, Docker or application update is required for this release.

## Compatibility and recovery

Official notes: [4.4.7](https://github.com/coollabsio/coolify/releases/tag/v4.4.7), [4.5.0](https://github.com/coollabsio/coolify/releases/tag/v4.5.0). All three installation artifacts remain byte-identical; 31 database migrations add features and convert data.

- Tokens need deploy permission for additional side-effect API routes. The existing read/write/deploy token remains appropriate. POST /api/v1/enable is removed; Solo VPS does not use it.
- Backup execution messages can be hidden without read:sensitive. Solo VPS now requires structured `s3_uploaded=true`; redacted messages no longer hide an unsuccessful upload. Additional token rights are unnecessary for this check.
- Compose scale/replicas above one are rejected on deployment. Review affected application Compose files before their next deployment. Existing workloads are not redeployed by this update.
- Existing ENV records retain legacy escaping. Re-saving or adding variables uses the new exact-value behavior.
- Additional stored secrets become encrypted with APP_KEY. Preserve database and APP_KEY together: an old image cannot reverse these migrations. The upstream encryption migration can catch per-table errors, so inspect migration logs and verify secret-backed functions after upgrading. Long invitation links may exceed the old column width; inspect outstanding invitations before upgrading. The qualified hosts had no nonblank values in the affected columns; a synthetic isolated fixture separately exercised encryption/decryption.
- Leave optional Coolify server patching disabled: Solo VPS owns host security updates. Native Coolify pre-update backup supplements its UI route; it does not replace Solo VPS checkpoints/off-host exports.

If interrupted, keep the same source and transaction marker and use the documented forward-resume procedure. Controlled interruption before artifact promotion does not prove arbitrary mid-migration crash recovery. Database recovery is a separate reviewed action; image-only downgrade is unsupported.

## Evidence and limits

Source tests, independent upstream/security review and controlled V3 evidence cover exact migrations on an isolated restored dump, synthetic legacy ENV/secret preservation, transaction interruption/resume, full verification/audit and a no-op rerun. UTC/Etc/UTC host verification also passed positive and negative runtime checks. See [test evidence](https://github.com/paracosm17/solo-vps/blob/v0.2.5/reviews/2026-10-24-coolify-450-runtime.md).

Bounded production V5 verify/audit and no-op passed. Original credentials, 120 stored ENV values and 18 application/proxy containers were preserved. All eight HTTPS response codes matched baseline, including two pre-existing development-route 404/503 responses. Sentinel was in sync; TLS WebSocket returned 101. See [production evidence](https://github.com/paracosm17/solo-vps/blob/v0.2.5/reviews/2026-10-24-coolify-450-production.md).

Fresh Coolify 4.5.0 installation/V4, a new live S3 integration replay and full application-data disaster recovery remain separate evidence gates. The S3 API correction has focused source tests and reviewed upstream boolean serialization; it is not a new claim of end-to-end S3 recovery.

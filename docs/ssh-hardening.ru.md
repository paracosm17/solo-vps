# Безопасное усиление SSH

SSH hardening намеренно отделён от первоначального host bootstrap. Цель — убрать рискованный bootstrap-доступ **только после** того, как управляемый администратор и provider recovery path действительно проверены.

## Перед началом

Не запускайте процедуру, пока не выполняются оба условия:

1. с рабочей станции открывается **новая** SSH-сессия под `admin.user`, а `sudo -n id -u` возвращает `0`;
2. доступен provider console/rescue, если SSH перестанет отвечать.

Не закрывайте текущую рабочую сессию во время изменения.

## Активируйте hardening

**Где: сохранённая VPS/контроллер-сессия**

```bash
SSH_HARDENING_CONFIRM=I_HAVE_VERIFIED_PROVIDER_RECOVERY SSH_HARDENING_ADMIN_LOGIN_CONFIRM=I_HAVE_VERIFIED_WORKSTATION_ADMIN_LOGIN make secure
```

Нижележащий workflow hardening проверяет сгенерированную конфигурацию OpenSSH до активации, перезагружает SSH только после успешных checks и затем запускает read-only verification.

## Проверьте через новую сессию

**Где: рабочая станция**

```bash
ssh <admin.user>@<server>
```

Затем на управляемом VPS/контроллере:

```bash
cd ~/solo-vps
make verify-ssh
make audit
```

Не закрывайте recovery/retained session, пока новый admin path не подтверждён.

## Если команда hardening завершилась ошибкой

Остановитесь и сохраните текущую рабочую сессию. Сначала прочитайте причину ошибки, а не начинайте править файлы вручную.

Если SSH недоступен, используйте provider console/rescue, проверьте управляемый SSH drop-in и восстановите доступ. Не ослабляйте постоянную policy только ради исчезновения необъяснённой ошибки.

## Почему процедура разбита на этапы

Добавить admin account безопасно, пока старый путь ещё работает. Отключение bootstrap/root/password access — критичное для доступа изменение. Разделение позволяет Solo VPS потребовать конкретные доказательства recovery и login до второго шага.

# 3. Сохраните историю логов в Grafana

После этой главы вы сможете находить записи приложения по времени и тексту, в том числе из контейнера, который уже заменён новым деплоем.

Сначала завершите [настройку VPS](../quick-start.md) и [доставку приложения](first-app.md). Для быстрого просмотра работающего приложения используйте **Logs** в Coolify. Эта глава добавляет поиск по истории.

  <div role="listitem"><span>1</span><div><strong>Приложение · VPS</strong><p>Приложение записывает запросы и ошибки в лог контейнера.</p></div></div>
  <div role="listitem"><span>2</span><div><strong>Grafana Alloy · VPS</strong><p>Агент читает эти записи и отправляет их по HTTPS.</p></div></div>
  <div role="listitem"><span>3</span><div><strong>Grafana Cloud · браузер</strong><p>Loki хранит записи. В Grafana вы ищете и скачиваете их.</p></div></div>
</div>

Второй VPS не нужен. Настройка собирает stdout/stderr — стандартный вывод приложений и сервисных контейнеров под управлением Coolify на этом сервере. Метрики хоста, логи сборок GitHub Actions и логи отдельно созданных баз данных в этот сбор не входят.

Перед включением проверьте, что логи приложений можно отправлять в Grafana Cloud. Агент не удаляет пароли, токены и персональные данные автоматически. При первом запуске он также может отправить уже имеющиеся записи контейнеров.

## Перед началом

Вам нужны работающее демо, SSH-доступ под настроенным `admin.user` и **одна и та же версия Solo VPS на компьютере и VPS**. Это первая последовательная глава, где служебные скрипты Solo VPS запускаются прямо на вашем компьютере.

Если каталог Solo VPS уже есть на компьютере, используйте его — скачивать проект повторно не нужно. Если локальной копии нет, подготовьте ту же версию, которую использовали для сервера:

- **Git:** клонируйте `<repository-url>`, перейдите в `solo-vps` и выберите тот же `<reviewed-revision>` из главы 1.
- **ZIP:** распакуйте на компьютере тот же ZIP Solo VPS и откройте терминал в каталоге проекта.

Компьютеру нужен Интернет для загрузки средств шифрования; VPS — исходящий HTTPS для загрузки Alloy и отправки логов. Используйте `SERVER_IP`, `ADMIN_USER` и домен приложения из базовых глав. Каталог исходников на VPS остаётся `~/solo-vps`.

В шагах 3 и 4 выполните вариант для своей ОС. Команды с пометкой **VPS** запускайте в SSH-сеансе, а не в локальном PowerShell.

## 1. Создайте аккаунт и stack в Grafana Cloud

**В браузере:**

1. Откройте [Grafana Cloud](https://grafana.com/products/cloud/) и нажмите **Create free account**.
2. Пройдите регистрацию предложенным способом; подтвердите email, если сервис попросит.
3. Откройте **Cloud Portal**. *Stack* — ваше рабочее пространство Grafana вместе с хранилищем логов.
4. Используйте stack, который появился после регистрации. На Free доступен один stack, поэтому дубликат создавать не нужно. Если у вас платный план и действительно нужен новый stack, используйте **Add Stack** в Cloud Portal и выберите там имя и регион хранения данных.
5. Откройте stack и нажмите **Launch** на карточке Grafana, чтобы перейти в её интерфейс. Портал оставьте в другой вкладке.

Если аккаунт уже есть, войдите и используйте существующий stack, в который хотите отправлять логи Solo VPS. Порядок регистрации и управления stack описан в [руководстве Grafana по началу работы](https://grafana.com/docs/grafana-cloud/learn-and-build/get-started/) и [руководстве по stack](https://grafana.com/docs/grafana-cloud/platform/security-and-account-management/account-management/cloud-stacks/create-update-stacks/).

До отправки логов проверьте **срок хранения** и **месячный лимит логов**. Сейчас Grafana указывает для Free 50 GB логов в месяц и минимум 14 дней хранения; условия сервиса могут меняться, поэтому сверяйтесь с [актуальными тарифами](https://grafana.com/pricing/) и страницей расхода/оплаты своего аккаунта. Для ошибки трёхдневной давности нужно не меньше трёх дней истории, для ошибки месячной давности — более длинное хранение.

**Ожидаемый результат:** в портале виден выбранный stack, его интерфейс Grafana открывается. Запишите выбранный срок хранения для последующей проверки истории.

## 2. Получите три значения для подключения

**В Cloud Portal:**

Откройте **Details** своего stack, затем **Details** на карточке **Loki / Logs**. Найдите пример **Sending Logs to Grafana Cloud using Grafana Alloy**. Сохраните значения `url` и `username` из этого примера. [Grafana описывает их расположение здесь](https://grafana.com/docs/loki/latest/operations/meta-monitoring/deploy/).

**Там же, в Cloud Portal:**

1. Откройте **Security → Access Policies**.
2. Нажмите **Create access policy** и задайте имя `solo-vps-logs`.
3. Если интерфейс предлагает выбрать realm или stack, укажите только stack из предыдущего шага.
4. Включите **Logs → Write** (`logs:write`). Права на чтение, удаление, метрики и администрирование этому агенту не нужны.
5. Создайте политику и нажмите **Add token**.
6. Назовите токен `solo-vps-alloy`, задайте срок действия, до которого сможете его заменить, и создайте токен.
7. Сразу сохраните значение в менеджере паролей: оно показывается только один раз.

Grafana размещает access policies в Cloud Portal в разделе **Security**. В некоторых вариантах интерфейса та же функция доступна внутри stack как Cloud access policies; подходит любой путь, если политика ограничена нужным stack и содержит только `logs:write`. Для отправки в Loki нужен [Cloud access policy](https://grafana.com/docs/grafana-cloud/platform/security-and-account-management/security-and-access/authentication-and-permissions/access-policies/create-access-policies/), а не токен Grafana service account.

Когда программа на компьютере попросит данные, используйте эту таблицу:

| Запрос программы / поле в файле | Что вводить |
| --- | --- |
| Grafana Cloud Loki push URL / `LOKI_URL` | Полный HTTPS-адрес `url`, оканчивающийся на `/loki/api/v1/push` |
| Grafana Cloud Logs user ID / `LOKI_USERNAME` | Числовое значение `username` из примера Loki |
| Grafana Cloud access-policy token / `GRAFANA_CLOUD_API_KEY` | Созданный токен с правом `logs:write` |

User ID — не email, не логин Grafana и не имя stack. Push URL — не адрес панели Grafana. Копируйте значения без окружающих кавычек. Если портал показывает только базовый адрес Loki, добавьте `/loki/api/v1/push` один раз.

**Ожидаемый результат:** все три значения сохранены в защищённом месте. Не вставляйте токен в команду, переменную GitHub, ENV приложения или сообщение в чате.

## 3. Подготовьте шифрование на компьютере

Solo VPS сохраняет зашифрованную копию данных подключения на вашем компьютере. Приватный ключ age позволяет расшифровать её и остаётся на компьютере.

### Windows PowerShell

**На компьютере, в каталоге Solo VPS:**

Если эта копия проекта получена из скачанного ZIP, Windows может пометить PowerShell-файлы как загруженные из Интернета. Один раз снимите эту метку со скриптов Solo VPS и запустите установщик:

```powershell
Get-ChildItem .\scripts\windows\*.ps1 | Unblock-File
.\scripts\windows\install-secrets-tools.ps1
```

Эта команда не ослабляет политику выполнения PowerShell. Если `Get-ExecutionPolicy` показывает `RemoteSigned`, оставьте её как есть. Для Solo VPS не нужно переключаться на `Unrestricted`.

Подготовьте ключ шифрования. Команду можно запускать повторно: если ключ уже существует, скрипт проверит его и **не заменит**.

```powershell
.\scripts\windows\new-age-key.ps1
```

Ожидайте `PASS Solo VPS age key created` или `PASS Solo VPS age key already exists`. Не удаляйте существующий ключ ради повторного запуска. Затем выполните:

```powershell
.\scripts\windows\init-sops-policy.ps1
.\scripts\windows\test-age-key.ps1
```

Ожидайте `PASS Solo VPS production age key SOPS roundtrip`.

Если вы уже проходили Solo VPS на этом компьютере, здесь могут остаться policy и зашифрованные файлы от прошлого запуска. Скрипт не удаляет их автоматически. При несовпадении recipient он покажет текущий ключ, старый recipient и количество `*.enc.yaml`.

Если старые зашифрованные файлы **нужны**, остановитесь и восстановите прежний age-ключ. Если вы просто заново проходите настройку и готовы снова ввести токены/пароли, выполните:

```powershell
.\scripts\windows\init-sops-policy.ps1 -StartFresh
```

`-StartFresh` ничего не стирает: старая policy и активные `*.enc.yaml` переносятся в `%LOCALAPPDATA%\solo-vps\archive\workstation-secrets\<дата-время>\`, после чего создаётся чистая policy для текущего ключа. Приватный age-ключ остаётся на месте. Затем снова выполните `test-age-key.ps1` и продолжайте главу.

Если PowerShell всё ещё блокирует скрипты после `Unblock-File`, откройте [раздел о секретах на Windows](../secrets-sops-age.md).

### Компьютер с Linux

**На компьютере, в каталоге Solo VPS:**

```bash
make secrets-tools
solo_age_keygen="$(python3 scripts/secrets_toolchain.py paths | sed -n 's/^age-keygen=//p')"
test -x "$solo_age_keygen"
mkdir -p ~/.config/solo-vps
chmod 700 ~/.config/solo-vps
if [ ! -e ~/.config/solo-vps/age-key.txt ]; then
    "$solo_age_keygen" -o ~/.config/solo-vps/age-key.txt
fi
chmod 600 ~/.config/solo-vps/age-key.txt
make init-sops-policy SOPS_AGE_RECIPIENT="$("$solo_age_keygen" -y ~/.config/solo-vps/age-key.txt)"
```

Здесь используется проверенная по контрольной сумме версия age, установленная проектом. Существующий ключ сохраняется. Остановитесь, если какая-либо команда завершилась ошибкой. На следующем шаге будет проверена расшифровка этим ключом.

Для обеих ОС сохраните восстанавливаемую копию `~/.config/solo-vps/age-key.txt` в подконтрольном вам месте вне этого компьютера. В Windows `~` означает каталог вашего профиля. Потеря всех копий означает потерю доступа к зашифрованным файлам. Не копируйте ключ в Git или на VPS. Если ранее выбрали другие пути ключа и состояния, передавайте те же пути скриптам.

## 4. Зашифруйте токен и передайте его на VPS

Перед этим шагом проверьте, что обычное SSH-подключение к `ADMIN_USER@SERVER_IP` работает. Скрипт доставки использует SSH без интерактивных запросов и sudo без пароля из базовой настройки. Если SSH-ключ защищён парольной фразой, сначала загрузите его в SSH-agent.

### Windows PowerShell

**На компьютере, в каталоге Solo VPS:**

```powershell
$ServerIp = 'YOUR_SERVER_IP'
$AdminUser = 'YOUR_ADMIN_USER'
.\scripts\windows\init-observability-secrets.ps1
.\scripts\windows\test-observability-secrets.ps1
.\scripts\windows\push-observability-secrets.ps1 -VpsHost $ServerIp -VpsUser $AdminUser
```

Если зашифрованного файла ещё нет, первая команда запросит три значения из шага 2; ввод токена скрыт. Если файл уже существует и подходит текущему ключу, helper проверит и переиспользует его без повторного ввода. При ошибке остановитесь. Если для SSH нужно явно выбрать ключ, добавьте к push-команде `-IdentityFile "$env:USERPROFILE\.ssh\your-admin-key"`, указав существующий ключ администратора.

Зашифрованный файл: `%LOCALAPPDATA%\solo-vps\state\secrets\observability.enc.yaml`.

### Компьютер с Linux

**На компьютере, в каталоге Solo VPS:**

```bash
SERVER_IP='YOUR_SERVER_IP'
ADMIN_USER='YOUR_ADMIN_USER'
make observability-secrets-init
make observability-secrets-check
make observability-secrets-push OBSERVABILITY_VPS_HOST="$SERVER_IP" OBSERVABILITY_VPS_USER="$ADMIN_USER"
```

По запросу введите те же три значения. При необходимости добавьте к push-команде `OBSERVABILITY_SSH_IDENTITY_FILE="$HOME/.ssh/your-admin-key"`. Зашифрованный файл по умолчанию находится в `~/.local/share/solo-vps/secrets/`; `make paths` показывает фактический путь.

Если `observability.enc.yaml` уже существует и расшифровывается текущим ключом, helper проверит его и **переиспользует без перезаписи**. Поэтому команды этой главы можно безопасно запускать повторно. Если хотите заново ввести Grafana credentials, используйте `-StartFresh` на шаге 3 или раздел [замены токена](#replace-a-token) ниже.

Если каталог исходников на VPS отличается от `~/solo-vps`, укажите `-RemoteProject` в Windows или `OBSERVABILITY_REMOTE_PROJECT` в Linux.

**Ожидаемый результат:** передача завершается сообщением `PASS workstation-to-VPS observability credential delivery`. Значения расшифровываются на компьютере и передаются через стандартный ввод SSH. Ключ age остаётся на компьютере. Этот шаг ещё не запускает Alloy и не даёт ему доступ к Docker.

## 5. Установите и запустите сбор

**Подключитесь с компьютера:**

```bash
SERVER_IP='YOUR_SERVER_IP'
ADMIN_USER='YOUR_ADMIN_USER'
ssh "${ADMIN_USER}@${SERVER_IP}"
```

**На VPS под администратором:**

```bash
cd ~/solo-vps
make verify-observability-credentials
make observability-tooling
make observability-runtime
```

Запускайте команды по порядку, при ошибке остановитесь. Проверка данных подключения читает `/etc/solo-vps/observability/grafana-cloud.json`, не выводя значения. Следующая команда загружает и проверяет закреплённую версию Grafana Alloy. Последняя запускает сбор и сама проверяет его состояние.

С этого момента Alloy отправляет логи подходящих контейнеров в выбранный stack. Solo VPS сам настраивает нужный Alloy доступ к Docker-логам; вручную расширять доступ к Docker не нужно. Настраивать Coolify Log Drain, устанавливать ещё один агент из мастера Grafana или открывать входящий порт не нужно.

В конце ожидайте `alloy_service: running/enabled`, `docker_api_proxy: running` и `current_invocation_diagnostic_errors: false`, без упавших задач Ansible. Это подтверждает работу агента. Доставку записи приложения отдельно проверим ниже.

## 6. Найдите запрос в Grafana

**В браузере** откройте адрес, заменив домен на домен демо:

```text
https://app.example.com/solo-vps-log-check-before
```

Демо намеренно вернёт `404` и `{"status":"not_found"}`: такого пути нет, зато запрос с уникальным текстом попадёт в лог. Данные приложения он не меняет. В **Coolify → приложение → Logs** найдите строку с `solo-vps-log-check-before`. Запишите дату, время и часовой пояс.

Для обычного поиска в этой главе **не нужен Explore и не нужен LogQL**. Используйте более простой интерфейс Grafana Logs Drilldown.

**В Grafana:**

1. В левом меню откройте **Drilldown → Logs**.
2. Вверху справа проверьте **Data source**. Выберите Loki-источник своего stack; обычно он называется `grafanacloud-<stack>-logs`.
3. Выберите диапазон **Last 15 minutes**.
4. На обзорной странице найдите карточку своего приложения. Для демо это обычно `solo-vps-demo`. Если имя другое, ориентируйтесь на приложение, которое только что записало запрос, и нажмите **Show logs**.
5. На странице приложения найдите блок **Line filter** над списком логов. Оставьте режим **Include** и в поле **Filter logs by string** введите:

```text
solo-vps-log-check-before
```

6. Должна остаться строка с этим путём. Нажмите её, чтобы открыть детали и увидеть время, `service_name` и другие поля/метки.

Grafana Logs Drilldown специально предназначен для просмотра Loki без написания запросов. [Официальное руководство](https://grafana.com/docs/grafana-cloud/learn-and-build/visualizations/simplified-exploration/logs/view-logs/) также использует **Drilldown → Logs**, **Show logs** и поле фильтра строки.

!!! note "В Grafana есть два похожих поиска"
    Для этой главы нужен **Line filter** над списком логов: он отбирает строки по тексту в выбранном диапазоне времени. Значок лупы в правой панели Logs открывает **client-side search** и ищет только среди уже загруженных строк. Если вы видите счётчик вроде `1/2` и стрелки вверх/вниз, это именно client-side search — закройте его и используйте **Line filter**. Переключатель **Code** здесь вообще не нужен.

Имя `service_name` приходит из Coolify и может отличаться от ожидаемого. Не угадывайте ID контейнера. Если приложений много, на обзорной странице можно использовать **Add label → service_name** или поиск по имени сервиса, затем открыть **Show logs**.

**Ожидаемый результат:** один и тот же запрос виден в Coolify и Grafana с временем и данными приложения. Одной успешной проверки агента недостаточно.

## 7. Проверьте историю после деплоя и перезапуска

Выполняйте упражнение на демо, когда другой деплой не идёт.

1. Убедитесь, что запись `before` из шага 6 уже видна в **Drilldown → Logs**.
2. В **Coolify → приложение** нажмите **Redeploy** и дождитесь успешного деплоя.
3. Откройте следующий адрес на том же домене приложения:

```text
https://app.example.com/solo-vps-log-check-after
```

4. Вернитесь в **Drilldown → Logs → ваше приложение**, выберите диапазон, охватывающий оба запроса, и в **Line filter** введите:

```text
solo-vps-log-check-
```

В списке должны быть и `solo-vps-log-check-before`, и `solo-vps-log-check-after`. Старая запись должна сохраниться после замены прежнего контейнера.

Теперь проверьте продолжение сбора после перезапуска агента. **На VPS под администратором, в каталоге Solo VPS:**

```bash
sudo systemctl restart solo-vps-alloy.service
make verify-observability-runtime
```

После успешной проверки откройте в браузере:

```text
https://app.example.com/solo-vps-log-check-restarted
```

С тем же **Line filter** должны быть видны уже три записи: `before`, `after` и `restarted`. Это подтверждает, что старая история пережила redeploy, а новые записи снова приходят после перезапуска Alloy. Такая проверка не гарантирует отсутствие потерь при произвольном сбое сети или агента.

Сохраните время исходной записи `before`. **Через три настоящих дня** откройте выбор времени в правом верхнем углу, задайте **Absolute time range**, который охватывает исходный запрос, и снова найдите `solo-vps-log-check-before` через **Line filter**. При повторении упражнения используйте новый суффикс, чтобы не принять старый результат за свежий.

## 8. Разберите старую ошибку

Когда пользователь сообщает об ошибке, сначала попросите примерное время, часовой пояс и, если есть, request ID или текст ошибки.

В Grafana откройте **Drilldown → Logs → нужное приложение**:

1. В выборе времени задайте **Absolute time range** вокруг события и проверьте часовой пояс.
2. В **Line filter** введите request ID, часть URL, `error` или другой текст, который должен быть в строке.
3. У нужной строки откройте меню **⋮ → Show context**, чтобы увидеть соседние записи до и после события.
4. Сравните время с **Coolify → Deployments**, чтобы понять, какая версия приложения работала тогда.
5. Если нужен файл, раскройте controls справа и используйте **Download logs**. Grafana умеет выгружать `TXT`, `JSON` и `CSV`. Проверьте выбранный диапазон и число строк перед передачей файла другим.

Logs Drilldown умеет показывать контекст строки и скачивать результаты; [эти действия описаны в документации Grafana](https://grafana.com/docs/grafana-cloud/learn-and-build/visualizations/simplified-exploration/logs/view-logs/). Ссылка или сохранённый фильтр не продлевают срок хранения.

### Если нужен LogQL

Для обычной эксплуатации он не обязателен. Если нужен сложный запрос, откройте меню **⋮** у панели логов в Drilldown и выберите **Explore**. Grafana перенесёт текущий контекст. Уже в **Explore** у Loki-редактора есть режимы **Builder** и **Code**; в **Code** можно, например, выполнить:

```logql
{job="solo-vps"} |= "solo-vps-log-check-"
```

Именно поэтому переключатель **Code** не виден на экране Logs Drilldown: это другой интерфейс. [Документация Loki query editor](https://grafana.com/docs/grafana/latest/datasources/loki/query-editor/) описывает Builder/Code внутри Explore.

Записи, удалённые до начала сбора, таким способом не вернуть. Логи старше срока хранения stack тоже могут исчезнуть. В своём приложении используйте структурированные логи с понятными ошибками и идентификаторами запросов; оставляйте request ID в содержимом строки, не создавайте отдельную метку потока для каждого ID.

## Если запись не находится

| Что видно | Что проверить |
| --- | --- |
| В Coolify Logs нет метки | Убедитесь, что домен ведёт на демо и запрос дошёл до него. Если приложение пишет только в собственные файлы, настройте вывод в stdout/stderr |
| В Coolify метка есть, в Grafana нет | Проверьте stack, источник Loki, диапазон времени и точный общий запрос из шага 6. Затем выполните `make verify-observability-runtime` на VPS |
| Агент не находит приложение | По умолчанию нужны метки `coolify.managed=true` и `coolify.type=application` или `service`. Отдельные БД и посторонние контейнеры исключены |
| Ошибки авторизации | Проверьте Logs user ID, push URL, срок действия токена и право `logs:write` для выбранного stack. При необходимости замените токен по разделу ниже |
| Запуск сообщает, что Alloy отсутствует | Выполните `make observability-tooling` на VPS, затем повторите `make observability-runtime` |
| Не проходит передача по SSH | Используйте существующий ключ администратора; проверьте SSH-agent, `SERVER_IP`, `ADMIN_USER` и каталог исходников. Передаче нужен sudo без пароля |
| Новые записи приходят, старые не видны | Проверьте абсолютный интервал, часовой пояс, срок хранения и работал ли тогда сбор |
| Записи дублируются | Проверьте, не отправляет ли те же логи второй агент или Coolify Log Drain |

При проблеме авторизации или сети проверьте соединение **одной синтетической записью**. **На VPS под администратором, в каталоге Solo VPS:**

```bash
make test-observability-loki
```

Команда отправляет фиксированное несекретное сообщение `solo-vps retained-log connectivity smoke` напрямую в Grafana Cloud. Ожидайте HTTP 204. Затем откройте **Drilldown → Logs**, выберите **Last 15 minutes**, нажмите **Add label**, выберите `job = solo-vps-smoke` и откройте **Show logs**. Успех подтверждает приём записи, но не сбор логов приложения. HTTP 401/403 указывает на авторизацию или права; 404 — на URL; 429 — на лимиты запросов/объёма; сетевые ошибки или 5xx — на соединение или провайдера.

Не расширяйте права Docker и не отправляйте полный дамп окружения для диагностики. Общие проблемы хоста разобраны в [диагностике сервера](status-and-logs.md).

## Замена токена {#replace-a-token}

Создайте новый токен для того же stack и политики по шагу 2. Сохраните предыдущий до проверки нового, кроме случая утечки, когда старый нужно отозвать сразу.

Создайте **новый зашифрованный файл**, проверьте его и явно передайте именно этот файл. Так рабочая копия останется целой. В Windows используйте `-OutputPath` у скрипта создания и `-EncryptedPath` у проверки/передачи; в Linux — `OBSERVABILITY_SECRET_FILE` для всех трёх Make-команд. Храните файл вне исходников и запишите, какой файл сейчас используется.

После передачи выполните `make observability-runtime` на VPS. Команда обновит файл данных подключения службы и при необходимости перезапустит Alloy. Найдите свежую метку в Grafana, затем отзовите предыдущий токен в Cloud access policies. Сохраните зашифрованный файл и ключ age среди материалов для восстановления.

## Готово: история доступна для поиска

Вы проверили настоящий запрос, старые и новые записи после деплоя и свежую запись после перезапуска агента. Проверка за три дня остаётся открытой до истечения этого времени.

Следите за сроком хранения, объёмом поступающих логов и датой окончания токена. Эта настройка добавляет логи приложений; метрики хоста и внешние уведомления о сбоях настраиваются отдельно.

**Дальше:** выберите следующую задачу в разделе [После базовой настройки](after-basic-setup.md). Если у приложения есть БД, в первую очередь проверьте копирование и настоящее восстановление.

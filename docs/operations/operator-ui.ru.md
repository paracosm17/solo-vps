# Как пользоваться платформой каждый день

После базовой настройки обычное обновление выглядит так: изменить код на компьютере, отправить его на GitHub, дождаться проверок и объединить изменения. Приложение на VPS обновится автоматически.

Эта статья объясняет путь из [второй главы](first-app.md): отдельный репозиторий приложения, GitHub Actions и приложение **Docker Image** в Coolify. Для собственного приложения нужно перенести этот workflow и настроить его тесты и Dockerfile.

## Кто за что отвечает

| Название | Что это означает для вас |
| --- | --- |
| Solo VPS | Подготавливает сервер: доступ, безопасность, Docker и Coolify |
| GitHub | Хранит код. Pull request позволяет проверить обновление до его выпуска |
| GitHub Actions | Выполняет тесты, собирает приложение и запускает деплой |
| GHCR / Packages | Хранит образы — пакеты с приложением и его зависимостями |
| Docker | Запускает образ в контейнере на VPS. Контейнер — работающий экземпляр приложения |
| Coolify | Даёт панель для приложений, доменов, переменных, баз данных и деплоев |
| Grafana | Позволяет искать сохранённые логи за выбранный период, когда сбор настроен |

**CI** — автоматическая проверка и сборка изменений. **CD** — доставка проверенного обновления на сервер. **Прод** — приложение, которым уже пользуются люди.

Solo VPS объединяет эти инструменты в повторяемый порядок настройки. После установки вам не нужно вручную копировать код на сервер и собирать его там при каждом изменении. Обслуживание сервера, резервные копии и исправление ошибок приложения остаются вашей ответственностью.

Push в рабочую ветку ещё не обновляет прод. Деплой запускается после изменения `main`, когда включена переменная `SOLO_VPS_DEPLOY_ENABLED`. Прямой push в `main` тоже может запустить деплой; используйте pull request, чтобы сначала увидеть результаты проверок.

**Digest** — точный идентификатор содержимого образа. Благодаря ему сервер получает именно тот образ, который проверил CI.

## Как выпустить следующее изменение

Сначала завершите или сохраните незакоммиченные изменения. **На компьютере, в каталоге репозитория приложения:**

```bash
git switch main
git pull --ff-only
git switch -c change-homepage
```

Для каждой новой задачи выбирайте новое имя ветки. Измените нужные файлы и запустите тесты своего приложения. Затем сохраните выбранные файлы в commit и отправьте ветку. В демо, если меняли только `app.py`:

```bash
git add app.py
git commit -m "Update homepage"
git push -u origin change-homepage
```

**На GitHub:**

1. Откройте **Pull requests → New pull request**.
2. Выберите base `main` и свою ветку, создайте PR.
3. Дождитесь успешных проверок. Если проверка красная, откройте её лог, исправьте ошибку и отправьте новый commit в ту же ветку.
4. Нажмите **Merge pull request → Confirm merge**.
5. В **Actions** откройте запуск для нового commit в `main`.
6. Дождитесь успешного **Deploy immutable image to Coolify**.
7. Откройте приложение по домену и проверьте результат.

В **Coolify → приложение → Deployments** видна история запусков. Для обычного выпуска через GitHub отдельно нажимать **Deploy** в Coolify не требуется.

## Как изменить настройку без изменения кода

Например, нужно поменять адрес внешнего API или текст, который приложение читает из переменной окружения.

**В Coolify → приложение → Environment Variables:**

1. Добавьте или измените нужные **Name** и **Value**.
2. Для настройки работающего приложения включите **Available at Runtime**.
3. Оставьте **Available at Buildtime** выключенным, если значение не нужно при сборке.
4. Нажмите **Save**.
5. Дождитесь завершения текущего CI-деплоя, если он идёт. Нажмите **Redeploy** и дождитесь успешного запуска.
6. Проверьте функцию, использующую эту настройку.

В демо `APP_MESSAGE` меняет поле `message` в ответе. Образ остаётся тем же: новый контейнер получает другое значение ENV.

Если приложение встраивает значение в файлы при сборке, как некоторые frontend-приложения, одного Redeploy недостаточно — потребуется новая сборка с настройкой на стороне CI.

## Где хранить пароли и токены

| Для чего значение | Где его задавать |
| --- | --- |
| Пароль БД, токен внешнего API работающего приложения | Coolify → приложение → Environment Variables |
| Доступ CI к деплою | GitHub → Settings → Environments → production → Environment secrets |
| Доступ агента логов или средства резервного копирования | В соответствующей инструкции настройки; проект хранит зашифрованную копию на компьютере |

Не вставляйте пароли в исходный код, Dockerfile и логи. Хранение значения в секрете не мешает приложению случайно вывести его. `APP_MESSAGE` для настоящего секрета не подходит: демо возвращает её клиенту.

При замене токена сначала обновите значение там, где оно используется, и проверьте работу. Затем отзовите старый токен, если сервис допускает такой порядок. Уже утёкший токен нужно отозвать сразу.

## Где искать логи

| Что хотите узнать | Куда идти |
| --- | --- |
| Почему не прошли тесты или сборка | GitHub → репозиторий → Actions → запуск → красный job |
| Почему не запустился новый контейнер | Coolify → приложение → Deployments → последний деплой |
| Что приложение пишет сейчас | Coolify → приложение → Logs |
| Что происходило три дня назад | Grafana → Explore, после настройки истории логов |

### Пользователь сообщил об ошибке три дня назад

1. Уточните время, часовой пояс, действие и, если есть, идентификатор запроса.
2. Откройте Grafana, выберите приложение и абсолютный диапазон времени вокруг ошибки.
3. Найдите запрос или текст ошибки. Посмотрите соседние строки.
4. Сопоставьте время с **Coolify → Deployments**: какая версия тогда работала?
5. Сохраните нужный фрагмент для расследования, убрав персональные данные перед передачей другим.
6. Исправьте причину в коде и выпустите изменение через обычный PR.

История появится только после настройки сбора. Удалённые до этого логи восстановить задним числом нельзя. Для расследования события месячной давности нужно хранить логи не меньше месяца.

Если приложение не пишет сведения о нужном действии, Grafana не сможет их придумать. Добавляйте в логи время, понятное описание ошибки и идентификатор запроса; пароли и токены туда не включайте.

## Если обновление не получилось

| Что видно | Что делать |
| --- | --- |
| Красные тесты или сборка в PR | Открыть первый упавший job, исправить код и отправить commit в ту же ветку. Этот PR ещё не менял прод |
| После merge образ собран, но Deploy остановился до подключения к VPS | Прочитать ошибку переменной, SSH или API. Исправить её и повторить упавший job для актуального `main` |
| Новый контейнер не прошёл проверку здоровья | Посмотреть Deployments и результат отката в Actions. Не запускать второй деплой, пока первый не завершился |
| CI сообщил timeout или потерял связь | Сначала посмотреть Coolify: операция могла продолжиться. Повторять её вслепую нельзя |
| Actions зелёный, но функция работает неправильно | Проверить функцию и её логи. Проверка здоровья не доказывает правильность всей бизнес-логики |
| Ошибка появилась после изменения ENV | Вернуть предыдущее значение в Coolify, выполнить Redeploy и проверить результат |

При подтверждённой ошибке новой версии helper может вернуть предыдущий образ. В логе `DEPLOY_FAILED_ROLLBACK_OK` означает, что прежняя версия снова стала healthy. CI остаётся красным, потому что выпуск не удался.

`DEPLOY_FAILED_ROLLBACK_FAILED` означает, что автоматическое восстановление тоже не завершилось. Откройте Deployments и используйте [инструкцию восстановления после деплоя](deployment-rollback.md). При неизвестном результате или таймауте автоматический откат не запускается, чтобы не пересечься с ещё работающей операцией.

**Откат образа не возвращает удалённые строки БД и не отменяет изменения её структуры.** Перед изменением данных нужен отдельный план резервного копирования и восстановления.

## Если приложение перестало открываться

1. Откройте домен с другого подключения, например через мобильный интернет. Запишите время начала сбоя.
2. Если Coolify доступен, проверьте состояние приложения, последний деплой и Logs. Сравните время сбоя с последними изменениями кода и ENV.
3. Если панель тоже недоступна, проверьте состояние VPS у провайдера.
4. Если VPS запущен, но обычного доступа нет, используйте консоль провайдера. Дальнейшие проверки — в [диагностике сервера](status-and-logs.md).
5. После восстановления проверьте публичный адрес приложения и сообщение внешнего монитора о восстановлении, если уведомления уже настроены.

Не начинайте расследование с переустановки Coolify или удаления контейнеров: это может уничтожить полезные следы ошибки и не исправить её причину.

## Что делать регулярно

Перед выпуском проверяйте PR; после выпуска — результат Deploy и изменённую функцию. Если появилась БД, проверяйте свежесть копий и периодически восстанавливайте копию в отдельную тестовую БД.

Следите за свободным диском, сроками токенов и сертификатов, уведомлениями о сбоях. Обновление приложения, обновление Coolify и обновление Ubuntu — разные операции. Для обслуживания сервера выбирайте отдельное окно. Практический порядок действий при failed deploy, ENV-ошибке, перезапуске агентов и reboot собран в [главе 8: сбои и обслуживание](incidents-and-maintenance.md); изменение версий Docker/Coolify остаётся в [руководстве обновления](../upgrades.md).

**Далее: [что добавить после базовой настройки](after-basic-setup.md).** Начните с истории логов, если текущего просмотра в Coolify уже недостаточно.

# 5. Получайте уведомления, когда приложение недоступно

Логи помогают разобраться **после** ошибки. Внешний монитор нужен для другого: он сам регулярно открывает ваше приложение и сообщает, если оно перестало отвечать.

Монитор работает не на VPS, поэтому уведомление может прийти даже тогда, когда сам сервер полностью недоступен.

В этой главе используем **UptimeRobot Free**. Для базового сценария отдельный VPS не нужен: бесплатный план проверяет HTTP(S)-адрес каждые 5 минут и умеет отправлять уведомления о падении и восстановлении.

## Перед началом

Нужен уже работающий публичный адрес приложения из главы 2, например:

```text
https://app.example.com/healthz
```

Используйте именно HTTPS-адрес приложения на обычном порту `443`. Не мониторьте Coolify `8000/6001/6002`, внутренний порт контейнера `8080`, SSH или Docker.

Сначала откройте `/healthz` в браузере или проверьте с компьютера:

```bash
curl -i https://app.example.com/healthz
```

Нужен ответ `HTTP 200`.

Если у вашего приложения ещё нет `/healthz`, добавьте простой публичный endpoint, который возвращает `200`, когда приложение готово принимать запросы. Не кладите в URL токены и другие секреты.

## 1. Создайте аккаунт UptimeRobot

Откройте [UptimeRobot](https://uptimerobot.com/) и создайте бесплатный аккаунт или войдите в существующий.

Для этой главы платный план не нужен. На Free проверки выполняются раз в 5 минут. Этого достаточно, чтобы узнать о недоступности небольшого проекта без собственной monitoring-инфраструктуры.

После входа откройте список **Monitors**.

## 2. Создайте HTTP monitor

Нажмите **Add New Monitor** или **New Monitor** и выберите **HTTP(s)**.

Заполните основные поля:

| Поле | Значение |
| --- | --- |
| URL | `https://app.example.com/healthz` |
| Friendly Name | понятное имя, например `solo-vps-demo` |
| Monitoring Interval | `5 minutes` на Free |
| Alert Contact | ваш email |

Если интерфейс предлагает timeout, `10 seconds` — нормальное стартовое значение. Остальные advanced-настройки для первого monitor не нужны.

Сохраните monitor и дождитесь статуса **Up**.

> Email/contact должен быть прикреплён именно к этому monitor. Само наличие email в аккаунте ещё не означает, что уведомления для него включены.

## 3. Проверьте канал уведомлений

Откройте созданный monitor и найдите **Test Notification**.

Отправьте тест на выбранный email и убедитесь, что сообщение реально пришло. UptimeRobot отправляет тестовые DOWN/UP notifications через тот же канал доставки, который будет использоваться при настоящем инциденте.

Не переходите дальше, пока тестовое сообщение не пришло. **Письма UptimeRobot, особенно первое, могут попасть в папку «Спам» / Junk.** Проверьте её и, если письмо оказалось там, отметьте его как «Не спам». Также убедитесь, что contact имеет события **Down** и **Up**.

## 4. Сделайте реальный короткий outage

Используйте **только демо-приложение или другой ресурс, который можно безопасно остановить**. Не выключайте production-приложение ради упражнения.

Перед остановкой убедитесь, что monitor показывает **Up**.

**В Coolify:**

1. откройте приложение `solo-vps-demo`;
2. нажмите **Stop**;
3. проверьте в браузере, что `https://app.example.com/healthz` больше не отвечает успешно;
4. ничего больше не меняйте и дождитесь UptimeRobot.

На Free очередная проверка может начаться почти сразу или почти через 5 минут. После неудачной проверки UptimeRobot делает дополнительные контрольные попытки, чтобы не объявлять Down из-за одного случайного сбоя. Поэтому сообщение **Down** не обязано прийти мгновенно.

Дождитесь одновременно двух фактов:

- monitor стал **Down**;
- на email пришло уведомление о недоступности.

Если через несколько минут monitor уже Down, а письма нет, сначала проверьте, что Alert Contact прикреплён к этому monitor.

## 5. Восстановите приложение

Вернитесь в Coolify и нажмите **Start**.

Сначала проверьте самостоятельно:

```bash
curl -i https://app.example.com/healthz
```

Снова нужен `HTTP 200`.

Затем дождитесь следующей внешней проверки. Monitor должен вернуться в **Up**, а на тот же email должно прийти уведомление о восстановлении.

Теперь проверено не только создание monitor, но и полный путь:

```text
приложение работает
→ внешний сервис видит HTTP 200
→ приложение остановлено
→ приходит DOWN
→ приложение запущено
→ приходит UP
```

## 6. Оставьте monitor включённым

После упражнения ничего удалять не нужно. Оставьте monitor активным — именно теперь он начинает приносить пользу.

Если планируете обслуживание, на бесплатном плане проще **временно Pause monitor**, выполнить работу и сразу снова **Resume**. Платные планы UptimeRobot также поддерживают Maintenance Windows.

Не используйте pause для обычных деплоев: нормальный rolling deploy из главы 2 не должен делать публичное приложение недоступным.

## Если уведомление не приходит

Проверьте по порядку:

1. `/healthz` действительно недоступен извне, а не только внутри Coolify;
2. monitor не стоит на Pause;
3. email/contact имеет статус Active;
4. contact прикреплён к нужному monitor;
5. включены события Down и Up;
6. проверьте папки «Спам» / Junk — outage/recovery письма UptimeRobot тоже могут попасть туда.

Если monitor остаётся **Up**, откройте его incident/check history и посмотрите, какой HTTP-ответ видит UptimeRobot.

## Что именно мы доказали

После этой главы внешний сервис независимо от VPS умеет заметить недоступность вашего публичного приложения и доставить DOWN/UP уведомления.

Короткая остановка приложения **не доказывает отдельно полную потерю VPS**. Перед публичным релизом Solo VPS этот более разрушительный сценарий проверяется на disposable/test server: VPS выключается из панели хостера, внешний monitor фиксирует Down, после включения — Up. На рабочем сервере ради документации этого делать не нужно.

Дополнительно можно посмотреть внутренний policy проекта без сетевых запросов:

```bash
make uptime-plan UPTIME_HEALTH_URL=https://app.example.com/healthz
```

Для обычной эксплуатации эта команда не обязательна.

**Готово:** если вы реально получили тестовое уведомление, DOWN и затем UP/recovery, глава завершена.

# После базовой настройки

Сервер настроен, приложение открывается по HTTPS, изменения из GitHub доходят до него автоматически. Теперь добавьте то, что понадобится при ежедневной работе: историю логов, резервные копии, уведомления о сбоях и метрики ресурсов.

Базовые главы 1 и 2 повторять не нужно. Выбирайте следующий шаг по тому, что уже есть у вашего приложения.

## Сначала разберитесь с ежедневной работой

[Как пользоваться платформой каждый день](operator-ui.md) показывает путь от изменения кода до работающей версии. Там же: где менять ENV, какие логи открывать и что делать, если выпуск не удался.

## 3. Сохраняйте историю логов

Если об ошибке сообщили через несколько дней, текущего окна Logs в Coolify может быть недостаточно. Отдельное хранилище позволяет искать записи по приложению, времени и тексту даже после замены контейнера.

В проекте для этого предусмотрены Grafana Cloud и агент Alloy на VPS. Агент отправляет логи, а вы читаете их в Grafana. Второй сервер для хранения и поиска обслуживать не нужно.

**Результат настройки:** вы находите запрос по уникальной метке, задаёте точный диапазон времени и видите эту же запись после нового деплоя. Затем проверяете, что она доступна через несколько дней в пределах выбранного срока хранения.

Перед включением выберите срок хранения и допустимый объём. Новое хранилище не вернёт логи, которые уже были удалены.

[Настройка истории логов](observability.md).

## 4. Добавьте резервные копии, когда появится БД

Для приложения с PostgreSQL начните с отдельной тестовой базы: запишите несколько строк, создайте копию и восстановите её в другую пустую базу. Сравните сами данные, а не только статус операции.

Локальная копия на том же VPS помогает вернуть данные после ошибки приложения. При потере диска или VPS она пропадёт вместе с оригиналом. Поэтому это первый этап, после которого ценным данным нужна копия вне сервера.

Начните с локальной копии на том же VPS: Coolify умеет создавать PostgreSQL backup по расписанию без S3. Затем обязательно восстановите её в отдельную тестовую БД и сравните данные.

[Пошаговая проверка PostgreSQL backup и restore](postgresql-backups.md) проводит этот тест от создания БД до восстановления сохранённой точки во времени. Расширенный [справочник PostgreSQL](../database-backups.md) остаётся для S3/API и более автоматизированного сценария.

**Результат настройки:** копия создаётся по расписанию, старые копии удаляются по выбранному правилу, а восстановленная тестовая база содержит ожидаемые данные. Основная база продолжает работать без изменений.

## 5. Получайте уведомления о недоступности

Логи не сообщат вам о сбое, пока вы сами их не откроете. Внешний monitor регулярно открывает публичный `/healthz` и сообщает, когда приложение перестало отвечать.

Для первого маршрута используем UptimeRobot Free: второй VPS не нужен, проверки выполняются снаружи, а DOWN/UP приходят на email.

**Результат настройки:** test notification пришёл, затем вы безопасно остановили демо-приложение, получили DOWN, снова запустили его и получили UP/recovery.

[Глава 5: внешние уведомления о недоступности](external-uptime.md).

## 6. Вынесите резервные копии за пределы VPS

Локальный backup помогает после ошибки приложения, но не после потери самого VPS. Следующий шаг — private S3-compatible storage вне сервера.

В одной последовательной главе вы отправите туда PostgreSQL backup, backup самой панели Coolify и зашифрованный restic snapshot нужных файлов `/data/coolify`. Затем восстановите PostgreSQL прямо из S3 в отдельную БД и докажете, что внешний backup действительно рабочий.

**Результат настройки:** рабочая копия данных доступна без локального файла на VPS, backup Coolify находится вне сервера, `restic` проходит restore-test, а ежедневный off-site timer включён.

[Глава 6: резервные копии вне VPS](offsite-backups.md). Полное [восстановление после потери VPS](../disaster-recovery.md) проверяется позже на отдельном replacement server.

## 7. Следите за CPU, памятью и диском

Логи объясняют, что происходило с запросами. Метрики показывают, что в это время происходило с самим VPS: росла ли нагрузка, заканчивалась ли память и сколько места осталось на диске.

Solo VPS использует отдельный лёгкий процесс Grafana Alloy и отправляет небольшой набор host metrics в тот же Grafana Cloud stack. Затем вы настраиваете один полезный disk alert и реально проверяете доставку email.

**Результат настройки:** CPU, memory и filesystem видны в Grafana Metrics Drilldown, alert на свободное место прошёл реальный `Firing → email → Normal` тест.

[Глава 7: метрики VPS](metrics.md). Application-level метрики вроде HTTP error rate добавляются отдельно, когда приложение само начнёт их экспортировать.

## 8. Разберите сбои и плановое обслуживание

Когда обычный путь уже работает, важно понимать разницу между красным PR, ошибкой сборки, неудачным deploy и реальным падением production. Отдельная глава собирает это в один порядок действий и добавляет checklist для ENV-ошибок, перезапуска агентов, замены CI API token и планового reboot.

**Результат:** вы знаете, когда production вообще не менялся, как читать `DEPLOY_FAILED_ROLLBACK_OK`, почему при timeout нельзя запускать второй deploy и что проверить до/после обслуживания. Сам destructive reboot ради проверки этой главы не требуется.

[Сбои и обслуживание](incidents-and-maintenance.md).

## Когда переходить к своему приложению

Приложение без ценных данных можно разворачивать после базовых глав. Перед размещением важной БД сначала проверьте резервное копирование и восстановление. Для приложения с пользователями добавьте историю логов и внешние уведомления.

Проходите по одной задаче: настройте, получите наблюдаемый результат, затем переходите дальше.

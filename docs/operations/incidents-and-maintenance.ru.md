# Разбирайте сбои и проводите обслуживание

Используйте эту инструкцию, когда CI красный, новый деплой не запустился, приложение перестало отвечать или серверу нужно плановое обслуживание.

Здесь не нужно специально ломать рабочий VPS. Цель — знать, **что изменилось, что осталось рабочим и где смотреть причину**, прежде чем нажимать Restart, Redeploy или запускать второй deploy.

Полная потеря VPS, восстановление на новом сервере и обновление Coolify между версиями описаны отдельно.

## Перед началом

Минимально должны быть завершены [часть 1](../quick-start.md) и [часть 2](first-app.md). В зависимости от выбранных дополнительных возможностей у вас также могут быть:

- Grafana для истории логов и метрик;
- UptimeRobot для внешней проверки `/healthz`;
- PostgreSQL backup/restore;
- off-site backup в S3-compatible storage.

Не все эти сервисы обязательны для любого приложения. В командах ниже запускайте проверки только тех компонентов, которые вы действительно настроили.

## 1. Различайте четыре вида неудачного выпуска

Не каждый красный GitHub Actions означает, что production сломан.

| Где произошла ошибка | Что произошло с production | Что делать |
| --- | --- | --- |
| Pull request: tests/lint/build | Ничего. Production не менялся | Исправить ветку и отправить новый commit |
| `main`: tests, migration preflight, publish или проверка image | Deploy ещё не начался. Старая версия продолжает работать | Исправить причину и сделать следующий обычный выпуск |
| Deploy нового image подтверждённо упал | Helper пытается вернуть предыдущий immutable image | Дождаться результата rollback и проверить приложение |
| Deploy завис/вернул timeout или неизвестный статус | Операция ещё может выполняться | **Не запускать второй deploy.** Сначала открыть Coolify → Deployments |

Пока GitHub не дошёл до шага **Deploy immutable image to Coolify**, откатывать production нечего.

## 2. Если pull request красный

**В GitHub → репозиторий приложения → Pull requests → ваш PR:**

1. Откройте красную проверку.
2. Найдите первый упавший step и прочитайте его ошибку.
3. Исправьте код в той же ветке.
4. Сделайте новый commit и `git push`.
5. Дождитесь зелёных проверок и только потом нажимайте **Merge**.

Не исправляйте такой сбой через Coolify. PR ещё не менял production.

## 3. Если выпуск из `main` сломался до деплоя

**В GitHub → Actions → запуск для commit в `main`:**

Посмотрите, какой job упал. Если красные **Application tests**, **Application migration preflight**, **Publish main image** или **Verify published image by digest**, job **Deploy immutable image to Coolify** не должен выпускать эту версию.

Откройте публичное приложение и `/healthz`. Там должна продолжать работать предыдущая версия.

Исправьте причину обычным PR. Не нажимайте **Redeploy** в Coolify только потому, что CI не дошёл до шага деплоя.

## 4. Если упал именно deploy

**В GitHub → Actions → красный job `Deploy immutable image to Coolify`:**

Найдите итог deployment helper.

### `DEPLOY_FAILED_ROLLBACK_OK`

Это означает:

```text
новый image не запустился
→ helper вернул предыдущий exact image
→ предыдущая версия снова running:healthy
→ CI остаётся красным, потому что новый выпуск всё равно не состоялся
```

Теперь:

1. Откройте **Coolify → приложение → Deployments** и убедитесь, что операции завершены.
2. Откройте публичный `/healthz`.
3. Откройте `/` и проверьте, что работает ожидаемая предыдущая версия.
4. В Grafana Logs при необходимости посмотрите строки вокруг времени неудачного deploy.
5. Исправьте новую версию обычным новым PR. Не пытайтесь сделать красный workflow зелёным ручным Redeploy старого образа.

Rollback здесь возвращает **только container image**. Он не отменяет migration БД, изменения данных, уже отправленные сообщения или другие действия во внешних системах. Для опасных изменений схемы или данных заранее нужен совместимый migration-план и backup.

### `DEPLOY_FAILED_ROLLBACK_FAILED`

Новый image не запустился, и автоматическое возвращение предыдущего image тоже не завершилось.

1. Не запускайте второй CI deploy.
2. В **Coolify → приложение → Deployments** дождитесь окончания текущей операции и посмотрите последнюю ошибку.
3. Проверьте текущий статус приложения в Coolify.
4. На VPS выполните read-only диагностику:

```bash
cd ~/solo-vps
make ops-status
make verify-coolify
```

5. Используйте точный known-good recovery path из лога CI и [справочник восстановления после неудачного деплоя](deployment-rollback.md). Не подставляйте `latest` вместо immutable digest.

### Timeout или неизвестный результат

Если helper пишет, что исход неизвестен, автоматический rollback намеренно не начинается: первый deploy ещё может работать.

Откройте **Coolify → Deployments** и дождитесь конечного состояния. Только после этого решайте, нужен ли новый выпуск или восстановление. Не запускайте одновременно CI-deploy и ручной Redeploy.

## 5. Если приложение упало без нового выпуска

Сначала выясните, это проблема приложения или всего VPS.

**Снаружи сервера:**

1. Откройте `https://app.example.com/healthz`.
2. Посмотрите UptimeRobot: если он тоже показывает DOWN, проблема видна независимо от вашего браузера.

**В Coolify:**

3. Откройте приложение и посмотрите его статус.
4. Откройте **Logs** и последние **Deployments**.
5. Если приложение просто остановлено и активного deploy нет, нажмите **Start** или **Restart**, затем снова проверьте `/healthz`.

**В Grafana, если она настроена:**

6. В **Drilldown → Logs** выберите время начала сбоя и посмотрите последние ошибки приложения.
7. В **Drilldown → Metrics** проверьте CPU, память и свободное место на `/`.

Если UI недостаточно, на VPS выполните:

```bash
cd ~/solo-vps
make ops-status
make verify
make audit
```

`make ops-status`, `make verify` и `make audit` не исправляют сервер автоматически. Они нужны, чтобы увидеть состояние до ручных изменений.

В итогах `make audit` слово `UNAVAILABLE` означает **«эта конкретная команда это не проверяла»**, а не поломку. Например, для Coolify используйте `make verify-coolify`, а для настроенного off-site backup — `make backup-status`. Если audit запускается прямо на VPS, capability report также может показать workstation-only SOPS policy/toolchain как `NOT_CONFIGURED` / `NOT_INSTALLED`: приватный age key и SOPS policy по дизайну остаются на вашем компьютере и не копируются на VPS.

Если не отвечает сам SSH, переходите в console/rescue вашего VPS-провайдера. Не ослабляйте firewall и SSH вслепую только ради восстановления входа.

## 6. Если ошиблись в ENV

Если приложение сломалось сразу после изменения Environment Variables, image может быть полностью исправен.

**В Coolify → приложение → Environment Variables:**

1. Верните предыдущее значение.
2. Нажмите **Save**.
3. Убедитесь, что сейчас не идёт другой deploy.
4. Нажмите **Redeploy**.
5. Дождитесь `Running (healthy)` и проверьте функцию, которая использует переменную.

Для секрета не копируйте старое значение из логов приложения. Берите его из password manager или другого места, где хранится актуальный секрет.

## 7. Перезапускайте агенты отдельно от приложения

Проблема Grafana не означает, что нужно перезапускать Coolify или приложение.

Если перестали приходить **логи**, на VPS:

```bash
cd ~/solo-vps
sudo systemctl restart solo-vps-alloy.service
make verify-observability-runtime
```

После этого сделайте один новый запрос к приложению и найдите его в Grafana Logs.

Если перестали приходить **метрики**:

```bash
cd ~/solo-vps
sudo systemctl restart solo-vps-metrics.service
make verify-metrics-runtime
```

Подождите один scrape interval и нажмите **↻ Refresh** в Grafana Metrics Drilldown.

Если не сработал backup, не перезапускайте всё подряд. Сначала:

```bash
cd ~/solo-vps
make backup-status
```

Чтобы сразу создать новый off-site snapshot, используйте:

```bash
make backup
```

Эта команда пишет во внешнее хранилище. Запускайте её только когда backup уже настроен по главе 6.

## 8. Замените Coolify API token до истечения срока

В главе 2 CI-токен создавался на 30 дней. Не ждите, пока следующий выпуск впервые обнаружит истёкший token.

**В Coolify:**

1. Откройте **Keys & Tokens → API Tokens**.
2. Создайте новый token с теми же минимальными правами: `deploy`, `write`, `read`; без `root` и `read:sensitive`.
3. Сохраните новый token в password manager. Старый пока не удаляйте, если он не скомпрометирован.

**В GitHub → репозиторий приложения → Settings → Environments → production:**

4. В **Environment secrets** обновите `COOLIFY_API_TOKEN` новым значением.
5. Следующий обычный выпуск должен закончиться успешным deployment.
6. После успешного deploy удалите старый token в Coolify.

Если token утёк, порядок другой: отзовите его сразу, затем создайте новый и обновите GitHub secret. Не оставляйте скомпрометированный token активным ради удобной проверки.

## 9. Подготовьтесь к плановой перезагрузке

Solo VPS не включает автоматический reboot после Ubuntu security updates. Если система сообщает, что перезагрузка нужна, выберите время, когда сможете сразу проверить сервер после возврата.

**Перед reboot на VPS:**

```bash
cd ~/solo-vps
make verify
make audit
```

Если настроена глава 6:

```bash
make backup-status
```

Также:

1. убедитесь, что в GitHub/Coolify нет активного deploy;
2. убедитесь, что последняя нужная PostgreSQL backup завершилась успешно;
3. проверьте `/healthz` перед началом окна обслуживания.

Только затем выполните:

```bash
sudo reboot
```

SSH-сессия оборвётся — это ожидаемо. Подождите загрузки и подключитесь снова под настроенным администратором.

**После reboot:**

```bash
cd ~/solo-vps
make verify
make audit
```

Если настроены главы 3, 6 и 7, дополнительно:

```bash
make verify-observability-runtime
make verify-metrics-runtime
make backup-status
systemctl list-timers solo-vps-backup.timer --no-pager
```

После команд проверьте снаружи:

- `/healthz` приложения;
- UptimeRobot должен вернуться в **UP**;
- в Grafana должны появляться свежие логи и метрики.

!!! note "Не перезагружайте production ради тренировки"
    Не делайте reboot рабочего VPS только ради галочки в документации. Используйте этот checklist, когда перезагрузка действительно нужна. Для отдельной репетиции возьмите disposable/test VPS.

## 10. Не обновляйте Docker и Coolify «заодно»

Проверить текущий поддерживаемый lifecycle можно read-only командой:

```bash
cd ~/solo-vps
make update
```

Она **не обновляет** Docker или Coolify.

Ubuntu security updates устанавливаются отдельно; автоматический reboot выключен. Major-версию Docker и версию Coolify меняйте только по [руководству обновления](../upgrades.md) и внутри диапазона версий, который поддерживает текущий Solo VPS.

Не включайте случайный `latest`, unattended Coolify upgrade или ручной package upgrade Docker только потому, что новая версия появилась upstream. Перед изменением платформы сначала нужны рабочие backup/recovery и понятный план проверки после обновления.

## 11. Короткий порядок действий при инциденте

Когда что-то сломалось, используйте один и тот же порядок:

```text
1. Что именно недоступно: приложение, Coolify, SSH или весь VPS?
2. Был ли прямо перед этим deploy, ENV change, update или reboot?
3. Есть ли ещё активная операция? Если да — не запускайте вторую.
4. GitHub/Coolify показывают ошибку выпуска или уже работающего приложения?
5. Grafana Logs объясняет ошибку приложения?
6. Grafana Metrics показывает нехватку CPU/RAM/disk?
7. Что показывают make ops-status / make verify / make audit?
8. Только после этого выполняйте минимальное исправление.
```

Не начинайте инцидент с `docker rm`, `chmod -R`, удаления `/data/coolify`, отключения firewall или пересоздания секретов. Такие действия уничтожают контекст и могут превратить локальную ошибку в проблему восстановления данных.

## Готово

Эта глава завершена, когда вы понимаете следующие границы:

- красный PR или build до deployment не меняет production;
- `DEPLOY_FAILED_ROLLBACK_OK` возвращает предыдущий image, но не состояние БД и не отменяет действия во внешних системах;
- при timeout/unknown status нельзя запускать второй deploy до завершения первого;
- приложение, сохранённые логи, метрики и резервное копирование проверяются отдельно;
- перед плановым обслуживанием есть исходная проверка и рабочие копии, а после — повторная проверка;
- Docker/Coolify upgrade не является обычным `apt upgrade` «заодно».

Для редких операций дальше используйте отдельные руководства: [обновление Docker/Coolify](../upgrades.md) и [восстановление после потери VPS](../disaster-recovery.md).

# Solo VPS

[English](README.md) · [Русский](README.ru.md)

**SSH, Docker, Coolify и деплой из GitHub — по одной инструкции.** Solo VPS настраивает Ubuntu 24.04, администратора, SSH, сетевой экран и Docker, затем устанавливает Coolify. Инструкция объясняет шаги в GitHub и Coolify для автоматического деплоя приложения.

Я сделал проект потому, что каждый новый сервер заставлял заново искать одни и те же команды: как создать SSH-ключ, добавить администратора, закрыть лишний доступ и поставить Docker. Сервер настраиваешь редко, а ошибиться в этих шагах легко.

> **Статус:** PRE-ALPHA — **пока не для production**. Используйте тестовый VPS. Автор проекта самостоятельно прошёл публичную инструкцию по установке и автоматическому деплою на чистом сервере; восстановление потерянного VPS проверялось отдельно. Релиз `v0.1.0` ещё не опубликован. Внешние копии и Grafana остаются дополнительными возможностями.

```text
ваш компьютер
        │
        │  setup → apply → secure → platform → verify
        ▼
Ubuntu 24.04 LTS VPS
        ├── защищённый сервер + Docker
        └── Coolify
              └── ваши приложения

GitHub Actions → GHCR → Coolify
SOPS + age → секреты для инфраструктуры и восстановления
Дополнительно: restic → внешнее хранилище копий
```

## Зачем я это сделал

Раньше выпуск выглядел так: `git push` на компьютере, затем SSH на сервер, `git pull`, `docker compose down` и `docker compose up`. Теперь GitHub Actions проверяет код и собирает образ, GHCR хранит его, а Coolify выполняет деплой. После `git push` сборка не нагружает VPS, и для каждого обновления не нужно заходить на сервер. В Coolify видны деплои, переменные и живые логи.

Проект автоматизирует настройку сервера и объясняет, как связать инструменты, сделать резервные копии и восстановиться после сбоя. Он рассчитан на одного разработчика или небольшой проект на одном VPS.

## Что такое Solo VPS

На чистом VPS с **Ubuntu 24.04 LTS** автоматизация настраивает и проверяет хост. Инструкция затем проводит через Coolify, первое приложение и его деплой из GitHub Actions. Для логов, внешних копий и восстановления есть отдельные главы.

После базовой настройки вы сможете:

- отправлять код в GitHub и автоматически выкатывать новую версию;
- управлять приложениями, доменами, HTTPS, переменными, базами данных и живыми логами через Coolify;
- проверять состояние сервера одной командой проекта;
- по следующим главам добавить историю логов, внешний мониторинг и резервные копии вне VPS.

## Компоненты

| Технология | Для чего она нужна | Почему она выбрана |
| --- | --- | --- |
| **Ubuntu 24.04 LTS** | Базовая операционная система | Стабильная, распространённая и предсказуемая основа для одного VPS |
| **Ansible** | Настраивает пользователей, SSH, сетевой экран, обновления и Docker | Позволяет повторить настройку и не редактировать сервер вручную десятками команд |
| **Docker** | Запускает приложения и сервисы в контейнерах | Даёт приложениям одинаковый формат и окружение запуска |
| **Coolify** | Деплои, домены, HTTPS, переменные, базы данных и живые логи | Даёт удобную панель для ежедневной работы без создания собственной платформы |
| **GitHub Actions + GHCR** | Проверяют код, собирают образы и передают их в Coolify | Связывают сборку и деплой с обычным `git push` |
| **SOPS + age** | Шифруют инфраструктурные секреты и данные для восстановления | Позволяют безопасно хранить зашифрованные файлы вне VPS |
| **restic + S3-совместимое хранилище** *(дополнительно)* | Хранят резервные копии отдельно от сервера | Потеря VPS не должна уничтожить его резервные копии |
| **Grafana Cloud и внешний uptime-мониторинг** *(дополнительно)* | История логов, метрики сервера и уведомления о сбоях | Помогают разобраться в проблеме, даже если VPS или старый контейнер уже недоступны |

Solo VPS рассчитан на один сервер. Он не управляет кластером и не заменяет Coolify. Базовая установка **не требует Tailscale, Grafana/Alloy, отслеживания ошибок, pgAdmin или настройки оболочки**.

## Текущий статус

Автор проекта самостоятельно прошёл базовый публичный маршрут на чистом VPS с Ubuntu 24.04 и коммитом `0fdba7f`: настройку хоста, защиту SSH, Coolify `4.3.21`, первое приложение и автоматический деплой. Приложенные логи показывают успешные `verify-coolify`, `verify`, `audit` и повторный `make platform` с `changed=0`. Это даёт базовому маршруту [V4 — подтверждение на чистом сервере](reviews/2026-09-28-clean-user-replay.md); последующие изменения до `dabf740` не затрагивают runtime-код или workflows. Отдельные проверки уровня V3 подтверждают обновление Coolify с продолжением после прерывания, восстановление потерянного VPS, восстановление PostgreSQL и restic, метрики и оповещения Grafana, историю логов и письма DOWN/UP при отключении всего сервера.

Alpha-версия не обещает надёжность production-системы.

Этот README описывает **то, что проект поддерживает сейчас**. [`ROADMAP.md`](ROADMAP.md) отражает оставшуюся работу. [`PROJECT_PASSPORT.md`](PROJECT_PASSPORT.md) описывает архитектурные решения, **а не текущую готовность реализации**.

## Что изменяет `make bootstrap`

`make bootstrap` настраивает базовую систему и входит в обычный запуск `make apply`. После предварительной проверки она может:

- настроить имя сервера и часовой пояс;
- создать отдельного администратора и проверить его доступ к sudo без пароля;
- настроить входящие соединения через UFW;
- включить автоматическую установку обновлений безопасности Ubuntu без автоматической перезагрузки;
- установить и настроить Docker Engine, Buildx и Compose.

Она **не устанавливает Coolify**, **не включает защиту SSH**, не создаёт секреты приложений, не подключает внешнее хранилище и не деплоит приложения.

При первой установке используйте `make apply`. Отдельные команды компонентов нужны для обслуживания и диагностики.

## Быстрый старт

Поддерживаемый alpha-путь — **один чистый VPS с Ubuntu 24.04 LTS**, минимум **2 vCPU, 2 GiB RAM и 30 GiB свободного места**. Нужны SSH-доступ под root, консоль восстановления провайдера, входящие TCP 22/80/443, домен с доступом к DNS и компьютер с Windows PowerShell или Linux, SSH и SCP. Make/Ansible из инструкции запускаются на VPS; для локальных Linux-инструментов на Windows подходит WSL.

Пройдите две части инструкции по порядку. В них собраны все обязательные команды и действия в интерфейсе, с примерами для Windows PowerShell и Linux. [Репозиторий исходников](https://github.com/paracosm17/solo-vps) уже открыт, но проверенного релиза и тега `v0.1.0` пока нет. Для pre-alpha тестирования клонируйте `main` по инструкции. Точный commit ID сохраняется в самой Git-копии; вводить хеш вручную не нужно. Меняющаяся ветка `main` пока не является проверенным релизом.

1. **[Настройте VPS и Coolify](https://paracosm17.github.io/solo-vps/ru/quick-start/)** — от `apt-get update` до доступа администратора, защищённого SSH, регистрации в Coolify и панели через HTTPS.
2. **[Запустите приложение и настройте CI/CD](https://paracosm17.github.io/solo-vps/ru/operations/first-app/)** — репозиторий GitHub, образ GHCR, первый деплой, отдельный CI-ключ и пользователь, настройки GitHub/Coolify, автоматический деплой, переменные приложения, секреты и живые логи.

Команды настройки сервера: `make setup → make apply → make secure → make platform → make verify`. Выполняйте их в местах, указанных в первой части, включая проверку входа под администратором перед защитой SSH.

Базовая настройка заканчивается после второй части. Внешние резервные копии, уведомления о сбоях и сохранение истории логов — следующие задачи; ссылки находятся в её конце.

**Ограничения alpha:** базовый путь подтверждён на чистом сервере; оформление и финальные проверки выпуска ещё открыты. Резервные копии, восстановление и наблюдаемость проверены отдельно. Solo VPS не обещает высокую доступность, определённое время доставки оповещений или фиксированный срок хранения логов.

## Безопасность

- Пока проект PRE-ALPHA, используйте тестовый VPS.
- Перед изменением SSH, sudo или сетевого экрана сохраняйте доступ к консоли восстановления провайдера.
- Не добавляйте в Git приватные SSH-ключи, ключи age, данные доступа к S3, пароли restic, API-токены или секреты приложений.
- UFW управляет входящими соединениями хоста; опубликованные порты Docker проверяются отдельно.
- Доступ к группе Docker фактически даёт права root. Его получает только уже привилегированный администратор.
- Проверки исходников не заменяют установку на чистом сервере, GitHub CI, настоящий внешний бэкап или восстановление.
